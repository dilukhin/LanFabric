# Интеграция Python 3.10 и внешнего интерфейса AWG

Дата: 2026-10-01. Статус: кандидат, проверка на реальном VPS ещё не выполнена.

## Исходные изменения

- Основа: PR #21, `agent/awg-autostart-0.0.18`, коммит `690849ee4c419c9eec3870ff78c8b37714a07b3c`.
- Источник улучшений: `agent/python310-v5-nat`, коммиты `6b99fb8badf92eb524377561b9fe0bc4ea24148b` и `95224d3f1c513c725f582cffd2f7d66559cca8c4`.
- Рабочая ветка: `agent/awg-python310-wan-integration`. Исходные ветки сохраняются.
- Версия обоих модулей сохраняется `0.0.18` из PR #21; отдельного изменения номера версии нет.

## Принятые решения

1. Минимум для двух рабочих модулей — Python 3.10. Проверки восстановления и доверенного интерпретатора root-службы допускают 3.10, сохраняя проверку владельца и прав пути. Это не меняет требования служебных скриптов `_bmad`.
2. Для AWG внешний интерфейс определяется по маршруту пересылаемого клиента с его исходным IP и входом `wg0`. Проверяются стандартные таблицы маршрутизации, единственный маршрут по умолчанию, тип и состояние внешнего интерфейса и два контрольных адреса. Пакеты контрольным адресам не отправляются.
3. NAT создаётся в `LANFABRIC-NAT`. Правила доступа остаются в `LANFABRIC-FWD`, защитный запрет — в `LANFABRIC-GUARD`. Общая блокировка изменений из PR #21 сохраняется.
4. Внешний интерфейс выбирается до замены участников. Он перепроверяется перед пересборкой правил, перед открытием защиты и при окончательной проверке. При ошибке защитный запрет сохраняется; восстановление после отказа не объявляется успешным.
5. Если активных клиентов с разрешённым интернетом нет, отсутствие внешнего маршрута не препятствует локальной VPN-сети.
6. При `add --internet` предварительная проверка выполняется до генерации ключей и записи учётной записи. Ошибка после записи прямо сообщает о сохранённой записи и незавершённом применении.
7. Маркированные внешние клиентские правила из исходной ветки NAT удаляются только по точной форме с метками `lanfabric-client-nat-v1` и `lanfabric-client-forward-v1`. После удаления проверяется их отсутствие; старый внешний интерфейс для удаления определять не требуется.
8. Клиентские правила ACCEPT/NAT, пересекающиеся с VPN-подсетью и не имеющие доказанной принадлежности, сохраняются; команда требует отдельной миграции. Правила для других подсетей не удаляются.

## Граница переноса

Этот этап переносит сетевые улучшения в защищённый механизм **AWG**. Прежний путь `wg`, включая `eth0`, остаётся отдельной задачей #19; нельзя распространять выводы об AWG на `wg`. Исходная ветка NAT сохраняет прежние изменения для последующей адаптации.

Смена внешнего маршрута сама по себе не запускает автоматическую пересборку. После стабильного изменения нужен штатный `sync`; если маршрут меняется во время применения, команда завершается ошибкой и оставляет защиту закрытой. Сложные правила выбора маршрута и несколько внешних выходов пока не поддерживаются.

Требование «активный Ethernet» относится к представлению сетевого интерфейса в ядре гостевой системы VPS. Поддержка иных типов интерфейсов требует отдельной проверки.

## Новая установка на v5

По уточнению пользователя от 2026-10-01 **действующих серверов 0.0.17 нет**. Миграция этой версии не является условием текущего этапа. Сведения о прошлых развёртываниях в документах и отчётах не описывают действующую инфраструктуру.

Перед новой установкой:

1. Через проверенный управляющий канал зафиксировать ОС, Python, состояние VPN, наличие и владельца `wg0`, внешние маршруты, правила FORWARD/POSTROUTING и независимый доступ SSH. Ключи и конфигурации в отчёт не включать.
2. Подтвердить отсутствие действующего VPN и конфликтующих остатков на v5. Отсутствие серверов 0.0.17 не является доказательством отсутствия любых старых файлов или чужих правил.
3. Подготовить ограниченное задание на новую установку с проверенным восстановлением, точными целями и проверками результата. Применение выполняется штатным `init` кандидата; `patch` старой версии не нужен.
4. После установки проверить клиентов, политики интернета и восстановление после перезагрузки без ручного `start`.

Прежний PR #21 автоматически удалял некоторые правила без меток. Интеграционный вариант не выполняет такого удаления. Если предварительная проверка выявит немаркированные клиентские правила, это отдельная задача доказательства принадлежности и точной очистки, а не обязательная миграция несуществующих серверов. Удаление произвольных правил или всей таблицы не допускается.

Идентификация целей и подтверждения `agent-safe`/`ssh_relay` остаются обязательными. Эта документация не разрешает запуск сессий, установку пакетов, изменение VPS или перезагрузку.

## Проверки

- Локальный набор `python tests_local/run_local_checks.py`; новые проверки фиксируют минимум Python, выбор маршрута, принадлежность правил, ошибку удаления, смену маршрута и сохранение запрета трафика.
- GitHub Actions: Ubuntu и Windows, Python 3.10/3.12/3.13, проверяется точный коммит ветки. Только локальные тесты; нет SSH, доступа к VPS, секретам и облаку.
- Отдельно нужны Windows-проверки местной установленной средой и чтение текущего v5 перед составлением исполнимого задания на установку.
- Реальная приёмка: внешний интерфейс `ens3`, интернет через v5, локальный обмен двух клиентов, блокировка/удаление клиента, повторный `sync`, сохранение посторонних правил и восстановление после перезагрузки без ручного `start`.
- Потерю маршрута и ошибки системных команд проверять в изолированном сетевом окружении, а не отключением управляющего маршрута реального VPS.

Локальные тесты и автоматическая проверка не доказывают реальную установку, работу пакетов AmneziaWG, клиентский трафик или восстановление после перезагрузки. Ubuntu 20.04 и сервер `vslava` этим этапом не добавляются в поддерживаемые платформы.
