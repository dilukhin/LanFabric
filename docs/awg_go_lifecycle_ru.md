# Штатная основа управления AWG Go

Дата: 6 октября 2026 года. Этап С2 задачи №28.

## Что изменено

После включения общей основы №29 в `master` добавлен отдельный путь управления
AWG Go — пользовательским процессом AmneziaWG, которому не требуется модуль ядра.
Основные скрипты остаются монолитными, SQLite не меняется, внешних зависимостей
Python нет. Версия 0.0.18 сохранена; новая версия и выпуск не назначены.

Это **основа жизненного цикла, а не готовый установщик**. Обычный `init` ещё не
выбирает и не доставляет Go. Отдельная служба v6 также не становится штатной
установкой от включения этого кода. Её перенос требует отдельной процедуры.
Не создавать описанное ниже состояние вручную на действующем сервере.

## Сохранённая реализация и компоненты

Протокол остаётся в `/opt/vpn-admin/backend`: только `awg` или `wg`.
Файл `/opt/vpn-admin/implementation` задаёт `kernel` (модуль ядра) либо `go`.
Отсутствующий файл означает прежнюю реализацию ядра; пустой, повреждённый или
недопустимый файл приводит к отказу. `go` разрешён только с `awg`.
Наличие исполняемого файла само по себе ничего не выбирает.

Для Go закреплены:

- `amneziawg-go`: `b5928efb6ca19f0153958460c3d141f04abc5c2e`;
- `amneziawg-tools`: `ee0f0a9aa34ff0a0da4b3433b9512781cfe02843`;
- платформа первой реализации: Linux x86_64.

Компоненты находятся в `/opt/vpn-admin/awg-go`, рядом с `manifest.json` —
описанием происхождения и контрольных сумм SHA-256. Проверяются структура
описания, закреплённые ревизии, платформа, контрольные суммы, обычный тип файлов,
отсутствие символических ссылок, принадлежность root и запрет посторонней записи
по всей цепочке каталогов. Код не скачивает компоненты и не создаёт их описание.

Контрольная сумма сравнивается с доверенным описанием установленного компонента.
Подтверждение происхождения при доставке, совместимость бинарных файлов с
Ubuntu 22.04/24.04 и поддержка Ubuntu 20.04 относятся к С3. Сборка в Ubuntu 24.04
для проверки не является универсальным пакетом поставки.

## Служба и восстановление

`lanfabric-awg-go.service` запускает Go в переднем плане на `wg0`.
Предварительная проверка и восстановление вызывают внутренние точки входа
штатного `vsrv-admin.py`. Запуск Go не требует проверки или загрузки модуля
`amneziawg` и не переходит на другую реализацию при ошибке.

Перед каждым запуском проверяются состояние, права, компоненты, отсутствие
конфликта интерфейса, сокета, порта и подсети. Сетевая защитная цепочка закрыта.
После появления процесса и управляющего сокета применяются сохранённый полный
профиль, серверный ключ, порт, активные участники SQLite, адрес, MTU 1280 и
политики сети. Открытие цепочки выполняется после сверки фактического состояния.
Новые ключи или параметры при восстановлении не генерируются.

Проверка принадлежности связывает MainPID службы, путь и аргументы процесса,
его группу systemd, тип TUN-интерфейса, публичный ключ сервера и владельца
управляющего сокета. Последний подтверждается через SO_PEERCRED — сведения
Linux о процессе на другой стороне локального соединения. Изменение PID
во время проверки приводит к отказу. Посторонние дополнения службы также
не принимаются.

Обычный и аварийный выход процесса вызывают повторный запуск systemd. После
SIGKILL может остаться сокет. Удаляется только сокет с ранее записанными
устройством, номером файла и временем изменения, если прежнее поколение
процесса уже умерло и сокет не принимает соединения. Подменённый, работающий
или неучтённый сокет не удаляется. Если авария произошла до записи доказательства
владения сокетом, автоматическое восстановление может безопасно остановиться.
Повторные неудачи ограничены политикой systemd; бесконечное ожидание запрещено.

## Команды и блокировки

Существующий `vcli-admin.py` передаёт прежние команды штатному серверному
скрипту. Для сохранённой установки Go сервер использует:

| Команда | Поведение |
| --- | --- |
| `start` | Запуск службы и проверка полного состояния; для уже работающего собственного процесса — синхронизация без перезапуска |
| `stop` | Остановка своей службы, проверка исчезновения процесса и интерфейса, очистка только собственных сетевых правил; данные сохранены |
| `restart` | Повторный запуск и полное восстановление сохранённого состояния |
| `sync`, управление участниками | Прежние SQLite и сетевые политики с закреплённой управляющей утилитой Go |
| `status`, `health` | Проверка реализации, процесса, интерфейса, профиля и сети без изменения состояния |
| `autostart enable/disable/status` | Управление разрешением запуска Go при загрузке, без остановки текущего процесса |
| `init`, `remove`, `purge` поверх Go | Отказ до очистки данных; установочный и удаляющий пути ещё требуют реализации и приёмки |

Долгие команды `start/stop/restart` сериализуются отдельной блокировкой операции.
Они не удерживают общую блокировку состояния во время ожидания systemd.
Служба получает только блокировку состояния и никогда не ждёт блокировку
операции. Это исключает взаимное ожидание команды и её дочерней службы.

Прежние AWG/WG-установки без файла реализации сохраняют свои пути работы.
Новый код не изменяет текущую служебную установку v6, доверие SSH/sudo,
схему SQLite, телефонные профили или клиентскую политику IPv6.

## Проверки и оставшаяся работа

Локальные проверки охватывают совместимость, повреждённую реализацию,
контрольные суммы и доверенные пути, подмену процесса/сокета, порядок блокировок,
повторный `start`, сохранение ключей, ошибки применения, конечное ожидание и
защиту от удаления чужого сокета.

Дополнительный сценарий GitHub Actions собирает закреплённые компоненты и
готовит **синтетическое состояние** в одноразовой Ubuntu 24.04. Затем настоящие
штатные команды проходят `start → start → sync → restart → stop → start`,
проверку полного профиля и SIGKILL с автоматическим восстановлением. Ключи,
описания профилей и вывод `showconf/dump` не публикуются. Сценарий отказывает
при существующих ресурсах VPN или вне собственного GitHub-hosted runner.
Этот стенд не проверяет телефоны, настоящий интернет-клиент или перезагрузку ОС.

Для завершения №28 остаются: проверяемая поставка и явный выбор при чистом
`init`; безопасное удаление; обновление компонентов и серверного модуля с
контрольным снимком и возвратом; перенос отдельной службы v6 без смены
профилей; установка на согласованном VPS и реальная клиентская приёмка.
