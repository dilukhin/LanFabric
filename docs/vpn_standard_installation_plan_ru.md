# Штатная установка и обновление VPN на следующих VPS

Дата: 4 октября 2026 года. Уточнение конечной цели пользователем.
Статус: принятый план развития; установка, поставка и совместимое обновление
реализованы через №31–№33. Перенос v6 и реальная приёмка не завершены.

## Конечный результат

LanFabric должен устанавливать и обслуживать VPN штатными `vcli-admin.py` и `vsrv-admin.py` на v6, v7, v8 и следующих VPS. Для обычной установки пользователю не нужны OpenCode, отдельное установочное задание, архив от агента, ручная сборка Go или ручное редактирование серверных файлов. Агент применяется при разработке и испытаниях, а не как обязательная часть эксплуатации.

LF-20261004-02 и отдельная служба из PR №26 — первый этап проверки выбранного AWG 3.1 на реальном v6. Успех этого этапа означает работающий конкретный сервер, но не готовность всего порядка установки LanFabric.

## Границы двух скриптов

| Компонент | Обязанности после интеграции |
|---|---|
| `vcli-admin.py` | Выбор сервера Windows/Linux, проверка SSH и версии, доставка выпуска и зависимостей, вызов установки/обновления, получение профилей в приватные файлы, понятные результаты и подсказки |
| `vsrv-admin.py` | Проверка ОС и архитектуры, постоянное состояние, выбранная реализация AWG, пользователи и права на интернет, собственные сетевые правила, служба, диагностика и восстановление |
| Выпуск LanFabric | Проверенные версии обоих скриптов, поддержанных Go/tools и совместимости; контрольные суммы, инструкции и сведения о предыдущем выпуске для возврата |

Третий установочный помощник допустим как временная заготовка. Его необходимые функции должны быть перенесены или включены в штатную управляемую поставку. Пользователь не запускает его отдельно и не обслуживает вручную две независимые установки.

Протокол AWG и способ исполнения — разные свойства: AWG в ядре и процесс Go не должны подменяться без явного сохранённого выбора. Действующие установки и прежние команды сохраняются; существующий сервер не переинициализируется при обновлении.

## Порядок обычной установки

1. Пользователь получает проверенный выпуск LanFabric и указывает новый сервер, например v7, с его SSH-доступом. Выпуски распространяются из канонического GitHub; разработчик может работать из Git по закреплённому коммиту. Ручной архив от агента не является обязательным входом.
2. `vcli-admin.py` проверяет идентичность сервера и доступность sudo, версии и необходимые зависимости. Новое доверие оформляется явно; существующее доверие не сбрасывается.
3. Штатная установка проверяет ОС, архитектуру, TUN, ресурсы, занятость порта, адресные конфликты и существующие правила. Изменять чужую установку или очищать глобальные правила нельзя.
4. Скрипты сами получают и проверяют нужные компоненты. Сборка Go на компьютере пользователя, обязательный PowerShell или агент не должны быть необходимы для штатного пути. Способ поставки бинарных компонентов и их проверка фиксируются до реализации этого этапа; автоматическая сборка выпусков может быть частью разработки.
5. Сервер сохраняет выбранную реализацию, порт, сеть, версии компонентов, ключи и пользователей. Устанавливает собственную службу и проверяет её фактическую готовность.
6. Администратор создаёт произвольных пользователей штатными командами, разрешает интернет и получает их профили. Имена dima/dina не должны быть зашиты в универсальную установку.
7. После импорта хотя бы одним реальным клиентом проверяются полезный трафик, DNS, исходящий адрес и поведение IPv6. Проверка службы на сервере сама по себе не доказывает доступность из РФ.

Ubuntu 20.04 остаётся отдельным требованием для чистых VPS. Однократный помощник Python 3.8 не делает основной `vsrv-admin.py` совместимым с этой ОС. До универсальной поставки нужно отдельно решить и проверить автоматическое обеспечение поддержанного Python либо совместимость серверного скрипта. Текущее требование основных модулей Python 3.10+ не изменено этим планом. Разрешение обновить Ubuntu на v6 не означает обязательного обновления ОС на всех будущих серверах.

Решение №33: [проверяемый приватный Python](awg_go_python20_ru.md), сохраняющий
системный Python 3.8 и ОС. Контейнерный прогон 20.04 прошёл; проверка со своим
ядром и холодной загрузкой VPS остаётся отдельной. Текущее состояние и точные
коммиты — [current_status_ru.md](current_status_ru.md).

## Порядок обновления

- Пользователь обновляет локальный выпуск и вызывает штатное обновление, основанное на существующей команде `patch`. Окончательное расширение команд определяется отдельной реализационной задачей; новые флаги этим документом не вводятся.
- Скрипты проверяют совместимость до остановки работающего VPN, подготавливают новые файлы отдельно и сохраняют приватное состояние для восстановления.
- Обычное обновление сохраняет серверные и клиентские ключи, HeaderProtectionKey, пользователей, их права, порт и сеть. Клиентам не приходится импортировать новые профили без реальной необходимости.
- Если меняется схема состояния, миграция выполняется явно и проверяемо. Прежнее правило «разная major/minor — только init» нельзя использовать как основание потерять действующие ключи.
- Переключение на новую версию заканчивается проверкой службы, полного применённого профиля и доступного клиента. При отказе возвращаются предыдущие компоненты и совместимое состояние; повреждённая установка не объявляется обновлённой.
- Повтор после обрыва SSH определяет фактический этап и продолжает или безопасно завершает его. Повторный запуск не вращает ключи и не дублирует службы/правила.
- Перенос отдельной установки v6 в штатное управление — отдельная миграция с сохранением профилей. Запуск `init` поверх неё не является миграцией.

## Телефоны и дополнительные компьютеры

Серверная установка не зависит от наличия телефона или vmasha. iPhone dina настраивается владельцем вручную. Android dima допускает установку приложения и передачу профиля через ADB (управление по USB); автоматический импорт зависит от фактически проверенного интерфейса приложения. Необходимые действия человека показываются отдельно. Секретные профили не публикуются в GitHub и отчётах.

Windows и vmasha проверяются следующим клиентским этапом. Каждому одновременно работающему устройству нужен отдельный ключ. Подключение vmasha не является условием установки нового VPS.

## Этапы и критерии завершения

| Этап | Результат, позволяющий перейти дальше |
|---|---|
| 1. Первая проверка v6 | Отчёт LF-20261004-02: фактические сборка, установка, сохранение профилей, реальный трафик и восстановление; недоступные телефоны отражены отдельно |
| 2. Интеграция в два скрипта | Сохранённая реализация Go, жизненный цикл и управление пользователями; перенос v6 без изменения профилей; прежние установки продолжают работать |
| 3. Универсальная поставка | Установка штатными командами с Windows и Linux; решены Python и доставка компонентов; пользователь ничего не собирает вручную |
| 4. Проверка следующего чистого VPS | Новый разрешённый собственный VPS, например v7, установлен штатным путём без архива от агента и ручных серверных исправлений |
| 5. Проверка обновления | Успешное обновление и контролируемый отказ с возвратом; профили/права сохранены; повтор после обрыва не повреждает состояние |
| 6. Выпуск для обычного использования | Документация, версии и проверенная поставка согласованы; v8 и следующие VPS используют тот же путь без нового индивидуального задания |

Этапы 2–5 можно готовить крупными итерациями, объединяя независимую разработку и проверки. Для испытаний нужен разрешённый собственный ресурс; чужие серверы не заменяют испытательный VPS.

v1/v4/v5 исключены. v2/vslava — только существующие резервные административные каналы, без VPN/испытательного трафика. v3, dilyavm и бот не затрагиваются. Этот документ не разрешает автоматически арендовать новый VPS, менять SSH-доверие или выполнять слияние PR.
