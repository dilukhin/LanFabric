Дата: 2026-09-18. Статус: инспекция включена в согласованный план; не разрешение на изменение сервера.

Текущая очередь и точка продолжения: [work_plan_ru.md](../work_plan_ru.md); актуальное состояние: [current_status_ru.md](../current_status_ru.md). ## 1. Вывод

Архитектура соответствует основной задаче: небольшая централизованная L3-сеть на готовом защищённом транспорте, с администрированием через SSH и управляемым выходом через VPN-сервер. Оснований переписывать проект, дробить модули на пакеты или срочно заменять сервер на P2P нет.

Проект продвинулся от исправления установки и управления доступом до работающего стенда с двумя физическими Windows-клиентами. Однако это пока проверенный прототип для контролируемой среды. Устойчивое восстановление после отказов и границы привилегий не доведены до состояния, достаточного для обещания автономной и безопасной эксплуатации.

Ближайший этап #12 выбран правильно. Его результат должен восстанавливать **данные, разрешённых участников и политики**, а не только создавать интерфейс. Обёртка systemd над неизменённым `start` недостаточна. Подробные замечания к соответствующему диалогу вынесены в [отдельный документ](LanFabric_awg_lifecycle_corrections_2026-09-18.md).

## 4. Оценка архитектуры

| Решение | Оценка и граница применимости |
|---|---|
| `vcli-admin.py` → SSH/SCP → `vsrv-admin.py` | Разумно для одного администратора и небольшого числа серверов. Нет дополнительного публичного API/демона. Требует строгой проверки SSH-хоста и безопасного обновления root-кода |
| WireGuard/AmneziaWG | Верно использовать готовый транспорт и явно хранить backend. Автоматическую подмену awg на wg сохранять запрещённой |
| SQLite как желаемое состояние | Подходит масштабу. Нужны строгая загрузка существующих данных и согласование с ядром/firewall; SQL-транзакция не делает внешние команды атомарными |
| Два монолитных Python-модуля, стандартная библиотека | Пока приемлемо: около 1,6 тыс. строк клиента и 1,2 тыс. сервера. Сначала выделять небольшие функции внутри модулей по ответственности, без массовой перестройки |
| Централизованный путь данных | Прост и наблюдаем. Сервер остаётся единой точкой отказа, задержки и стоимости трафика; производительность и предел числа активных клиентов не измерены |
| iptables и netfilter-persistent | Работает на выделенном стенде, но владение правилами не изолировано. Совместимость с чужими правилами, порядком загрузки и отказами требует доработки |
| systemd для загрузки AWG | Подходит. Отдельная задача восстановления и полноценное управление всем жизненным циклом — оба допустимые варианты при согласованном контракте |

Не нужен `BackendManager` только ради абстракции. Полезнее разделить внутри существующего сервера: проверку сохранённых данных, построение желаемого состояния, применение, проверку результата и безопасный отказ. Это устраняет дублирование init/start/sync без смены структуры проекта.

## 5. Приоритетные находки

P1 — существенный риск безопасности/восстановления, который следует закрыть до соответствующей эксплуатационной возможности. P2 — важная отдельная доработка. Это оценка инспекции, а не формальная классификация уязвимости.

### F1. Частичное применение может оставить VPN без запрета трафика — P1

`cmd_sync` снимает общий DROP и затем по очереди возвращает peers. При отказе между этими действиями интерфейс и часть peers остаются, а DROP отсутствует. Аналогичные перестановки есть в firewall helpers. Очистка в `finally` не заменяет отсутствие опасного промежуточного состояния: процесс может быть прерван.

Изолированная модель фактического кода с двумя пользователями без интернета и ошибкой на втором peer дала `interface_up=true`, один восстановленный peer, `drop=false`. Возможность реального неразрешённого обмена зависит от остальных правил, маршрутизации и общей политики FORWARD; на dilyavm она не проверялась.

Кроме того, общая блокировка изменения состояния отсутствует. Одновременные boot/start и block/remove способны применять разные снимки БД. `sync` удаляет и повторно добавляет всех peers, поэтому его нельзя считать проверенным бесшовным повторным действием. Задача: [#15](https://github.com/dilukhin/LanFabric/issues/15). Источник: [firewall/start](https://github.com/dilukhin/LanFabric/blob/51df21abd770dbc47655317d870b4f73e080dc35/vsrv-admin.py#L267-L410), [sync](https://github.com/dilukhin/LanFabric/blob/51df21abd770dbc47655317d870b4f73e080dc35/vsrv-admin.py#L886-L921).

### F2. Восстановление создаёт потерянные данные — P1

`start` через `ensure_awg_setconf` → `build_setconf` → `get_or_create_awg_params` генерирует новые параметры, если файл утрачен. Это нарушает соответствие ранее выданным конфигам. `init_db` создаёт отсутствующую БД даже из status/health/sync: потеря пользователей маскируется пустой таблицей.

Восстановление должно требовать существующие валидные данные; создание разрешено отдельному пути инициализации. Валидная существующая БД с нулём пользователей допустима. Задача: [#17](https://github.com/dilukhin/LanFabric/issues/17). Источник: [параметры AWG](https://github.com/dilukhin/LanFabric/blob/51df21abd770dbc47655317d870b4f73e080dc35/vsrv-admin.py#L215-L265), [БД](https://github.com/dilukhin/LanFabric/blob/51df21abd770dbc47655317d870b4f73e080dc35/vsrv-admin.py#L480-L497).

### F3. Диагностика не является надёжным критерием готовности — P1

`health` накапливает ошибки и печатает их, но не возвращает ненулевой код. В воспроизведении отсутствовали интерфейс и другие необходимые условия, а main завершился с кодом 0. `status` для AWG проверяет существование интерфейса и возможность awg show, но не UP/адрес/точное соответствие peers. `health` не сравнивает весь набор peers/AllowedIPs с БД и не подтверждает весь NAT-контракт.

Поэтому прежний принятый E2E, где дополнительно проверялись handshakes/маршруты/трафик, не обесценивается. Но future-проверка вида «health exit=0, значит PASS» недопустима. Задача: [#17](https://github.com/dilukhin/LanFabric/issues/17). Источник: [status/health](https://github.com/dilukhin/LanFabric/blob/51df21abd770dbc47655317d870b4f73e080dc35/vsrv-admin.py#L671-L884).

### F4. Владение кодом root-службы и права БД — P1

`copy_server_module` делает каталог `/opt/vpn-admin` собственностью SSH-пользователя, затем SCP записывает модуль прямо в окончательный путь. Такой файл нельзя без отдельного решения считать защищённой точкой запуска systemd от root. Замены владельца самого файла недостаточно, если его родительский каталог остаётся доступен на запись.

БД хранит закрытые ключи всех VPN-пользователей. При обычной umask 022 локально воспроизведены права 0644 у БД и 0755 у каталога: код не устанавливает закрытую границу. Фактические права dilyavm здесь не измерялись.

Текущий sudoers с apt/systemctl/chown/rm также нельзя трактовать как надёжное ограничение «только функции VPN». SSH-оператор фактически должен рассматриваться как полноценный администратор сервера, пока более узкая модель не спроектирована. Задача: [#16](https://github.com/dilukhin/LanFabric/issues/16). Источник: [копирование](https://github.com/dilukhin/LanFabric/blob/51df21abd770dbc47655317d870b4f73e080dc35/vcli-admin.py#L399-L411), [sudoers](https://github.com/dilukhin/LanFabric/blob/51df21abd770dbc47655317d870b4f73e080dc35/vcli-admin.py#L631-L642).

### F5. SSH-проверка хоста и конфигурационный канал — P1/P2

SSH/SCP используют `StrictHostKeyChecking=no`. Успешный независимый strict SSH в предыдущем испытании не доказывает строгую проверку самого LanFabric. Непотоковый `exec_remote` объединяет stderr и stdout: предупреждение может попасть в скачиваемый конфиг. Режимы потокового/TTY-исполнения не применяют конечный timeout.

Нужны согласованное доверие ключу хоста, раздельные каналы данных и диагностики, проверка и атомарная запись конфига, конечные сроки. Задача: [#18](https://github.com/dilukhin/LanFabric/issues/18). Источник: [SSH](https://github.com/dilukhin/LanFabric/blob/51df21abd770dbc47655317d870b4f73e080dc35/vcli-admin.py#L88-L171).

### F6. Загрузка backend wg не восстанавливает SQLite peers — P1 для wg

LanFabric создаёт `wg0.conf` только с Interface и PostUp/PostDown. Peers добавляются через `wg set`, но в этот конфиг не записываются. Ручной `cmd_start` вызывает sync после запуска wg-quick; загрузочный `wg-quick@wg0` этого не делает. Значит, active-служба сама по себе не означает восстановленных пользователей.

Это статический вывод по прослеженному пути, а не новый cold-boot E2E. Задача: [#19](https://github.com/dilukhin/LanFabric/issues/19). Источники: [создание конфига](https://github.com/dilukhin/LanFabric/blob/51df21abd770dbc47655317d870b4f73e080dc35/vsrv-admin.py#L624-L647), [штатный unit WireGuard](https://git.zx2c4.com/wireguard-tools/tree/src/systemd/wg-quick@.service). Не следует автоматически переключать действующий AWG-стенд на wg для проверки.

### F7. Обновление и имена файлов не имеют достаточных ограничений — P2

Сравнение версий отличает patch от major/minor, но не направление обновления: смоделированное `server=0.0.18/client=0.0.17` вызывает копирование и принимает понижение. SCP пишет окончательный файл без атомарной замены. Имя VPN-пользователя напрямую входит в путь `.conf`; `../escaped` в локальном примере выходит из каталога конфигов. Это особенно опасно как ошибка оператора; доступ уже требует административных полномочий, поэтому отдельная эскалация привилегий этим примером не доказана. Учтено в [#16](https://github.com/dilukhin/LanFabric/issues/16).

### F8. Удаление и повторы могут сообщать успех при неполной очистке — P2

`stop`, cleanup и удаление пакетов широко используют `|| true`/`check=False`. Состояние после отказа удаления интерфейса не подтверждается перед снятием firewall. `purge` охватывает `/etc/wireguard` целиком и пакеты; это допустимо только при явно выделенном сервере/подтверждённом владении. Отдельные destructive-проверки остаются нужны; не выполнять их ради инспекции.

## 6. Соответствие пользовательской задаче и скрытые ограничения

- **L3 не означает обычную Ethernet-LAN.** Есть IP-связность; автоматическое обнаружение серверов через broadcast/multicast и требующие L2 игры пока не обеспечены. Нужен настоящий сеанс хотя бы одной игры с подключением по IP; обнаружение проверять отдельно. #8 уже корректно разделяет эти задачи.
- **Интернет-политика относится к выходу через VPN-сервер.** `internet=НЕТ` не отключает обычный интернет телефона/ПК. `admin` сейчас не является ролевой моделью; все активные участники получают общее разрешение wg0→wg0. Попрограммных/попарных ACL и комнат нет.
- **Защита самого сервера отдельно.** Правила FORWARD не задают политику INPUT к службам на VPN-шлюзе. До добавления недоверенных участников следует определить доступные им серверные порты.
- **IPv4 и конфиденциальность.** Конфиги и правила ориентированы на IPv4; маршруты `/1 + /1` в Windows намеренно обходят kill-switch. Это решает управление сетью, но не доказывает отсутствие утечек IPv6/DNS и не является обещанием анонимного full-tunnel.
- **Переносимость.** Жёсткие `eth0`, `10.8.0.0/24`, порт, DNS 8.8.8.8 и имя wg0 требуют проверки конфликтов. В адресном пуле 253 клиентских адреса; это не измеренная производительность. Пересечение VPN-подсети с локальной сетью и MTU ещё нужно испытать.
- **Windows Firewall.** Ограничение ICMP у Alice обоснованно не признано серверным дефектом. Для пользователя невозможность подключения игры всё равно требует понятной диагностики профиля и нужных портов, без общего отключения firewall.
- **Android.** Следующий этап оправдан и должен проверять Windows↔Android, Wi-Fi↔мобильную сеть, DNS, отдельные ключи и маршрутизацию. Флаги «подключено» и один handshake недостаточны. Совместимость установленных AWG-пакетов/модуля ядра/клиентов фиксировать в отчёте конкретными версиями.
- **Адрес сервера и резервное восстановление.** Автозапуск гостевой службы не запускает выключенную VM и не обновляет Endpoint в клиентских конфигах после смены публичного IP. Нужны отдельные решения о стабильном адресе/имени и проверяемой резервной копии. Изменять облако сейчас не требуется.

Код 0 этого скрипта означает подтверждение описанных проблем версии 0.0.17, **не** прохождение приёмки исправлений. После исправления поведение и ожидания нужно заменить настоящими регрессионными тестами.

Существующие 84 теста сосредоточены преимущественно на trust, установке, версиях и Windows-конфигах. Успех набора не доказывает покрытие отказов lifecycle/firewall. В дереве master отсутствует `.github`; Connector не вернул PR-triggered Actions runs для проверяемого SHA. Настроенной в репозитории CI-проверки не обнаружено. Ответ branch API содержит `protected=false`; автоматически включать защиту ветки инспекция не требует.

Тестовый runner допускает expected failures, тогда как E2E-план требует их отсутствия. Сейчас их ноль, поэтому это несоответствие не отменяет PASS, но правило следует согласовать перед добавлением новых тестов. В README ещё перечислены общие направления развития, а принятый порядок хранится в current_status; при планировании использовать последний.

## 8. Рекомендуемый порядок

1. Уточнить контракт #12 по отдельному документу: строгое восстановление, проверяемая изоляция, блокировка операций, доверенный root entrypoint и реальные признаки готовности. Релевантные части #15–#17 являются условиями этого этапа; полное выполнение всех новых issues не требуется автоматически.
2. Реализовать согласованное решение небольшой отдельной задачей. Решение о 0.0.18, обновлении/миграции и допустимом перерыве связи принять явно; в инспекции версии сохранены.
3. Выполнить отдельную приёмку cold boot без ручного start, с неизменностью пользователей/ключей/параметров/политик и реальным клиентским трафиком. Не повторять уже закрытый deployment/E2E без конкретной причины.
4. Продолжить утверждённый #11 Android. До доступа недоверенных пользователей закрыть соответствующие задачи безопасности #16/#18 и политику доступа к самому серверу.
5. Проверить wg по #19 отдельной задачей, не разрушая AWG-стенд. Реальную игру/MTU/производительность включить в следующий прикладной этап по отдельному решению.
6. Сохранить #8 STUN/ICE/P2P исследованием после надёжного центрального варианта; не смешивать собственный сетевой транспорт с исправлением эксплуатации.

Пункты 4–6 уточняют будущую работу и не заменяют автоматически утверждённую дорожную карту. Код, версии, VM, systemd, firewall, agent-safe и yc-guard этой инспекцией не изменялись.
