# LanFabric — Project Baseline

Статус: действующий устойчивый baseline  
Дата: 2026-08-20

Этот документ содержит долговечные факты и инварианты проекта. Текущая реализация определяется фактическим состоянием репозитория, а не этим документом.

## 1. Идентичность проекта

Канонический репозиторий: `dilukhin/LanFabric`  
Каноническая default branch: `master`.

LanFabric — CLI-инструменты управления VPN на базе WireGuard/AmneziaWG для организации локальной L3-сети с управляемым доступом клиентов в интернет.

Архитектура:

```text
администратор Windows/Linux
        |
        | vcli-admin.py
        | SSH/SCP
        v
Ubuntu server
        |
        | vsrv-admin.py
        | WireGuard / AmneziaWG
        | SQLite / iptables / systemd
        v
VPN-клиенты
```

## 2. Технологические инварианты

- Python 3.12+.
- Только стандартная библиотека Python.
- Сервер: Ubuntu 22.04/24.04.
- Клиент администратора: Windows/Linux.
- Серверные действия выполняются через `sudo`.
- Допустимые backend: только `awg` и `wg`.
- Silent fallback `awg -> wg` запрещён.
- Backend выбирается при `init` и сохраняется на сервере.
- Структура `vcli-admin.py` и `vsrv-admin.py` остаётся монолитной без отдельного архитектурного решения.
- Не добавлять внешние Python-зависимости, pytest/ruff/black/mypy и аналогичную инфраструктуру без отдельного решения.

## 3. Версионирование

В начале каждого runtime-модуля:

```python
__version__ = "major.minor.patch"
```

Текущую версию всегда читать из фактического HEAD обоих модулей; не полагаться на старые отчёты или планы.

Семантика:

- полное совпадение — обычные команды разрешены;
- отличается только patch — требуется `patch`;
- отличается major или minor — требуется переинициализация через `init`;
- изменение `__version__` выполняется только по явному заданию.

## 4. UX и CLI

Проект рассчитан на пользователя, которому нужны подсказки и защита от неверных действий.

- CLI расширяется через `argparse`.
- Краткий и полный `--help` — на русском.
- Ошибки должны объяснять следующий безопасный шаг.
- Опасные действия требуют явных подтверждений.
- Комментарии, docstrings, help, сообщения, ошибки и рекомендации — на русском.
- Для документационных примеров использовать SSH-пользователя `donpedro` и сервер `198.51.100.42`.
- Clean-stdout команды нельзя загрязнять логами/diagnostics.

## 5. Security-инварианты

Никогда не публиковать и не выводить в отчёты:

- приватные SSH/WireGuard/AmneziaWG/Yandex Cloud ключи;
- пароли и sudo-пароли;
- токены, cookies, authorization headers;
- содержимое `PrivateKey` в VPN-конфигах;
- service-account key JSON и конфигурацию YC с секретными полями.

Security-sensitive области:

- SSH trust, `authorized_keys`;
- sudo/sudoers;
- iptables/firewall;
- systemd;
- SQLite schema;
- генерация/ротация ключей;
- `init`, `patch`, `remove`, `purge`, `trust`, `untrust`;
- Yandex Cloud IAM, ключи, firewall, диски, backup restore и ресурсы, влияющие на стоимость.

Изменение этих областей требует отдельного bounded task и явного разрешения там, где действие реально меняет инфраструктуру.

## 7. Модель разработки

Используется Web-first workflow:

- ChatGPT Web выполняет архитектуру, research, анализ репозитория, проектирование, review, подготовку bounded task и GitHub remote writes через Connector.
- OpenCode выполняет только то, что требует локальной Windows-среды, локальных инструментов, SSH к тестовой ВМ, `yc` через guard либо локального тестового запуска.
- Архитектурные решения остаются за ChatGPT Web.
- Для нетривиальной задачи применяется BMAD/OpenSpec-lite task card.
- Результат агента возвращается в Web как отчёт + минимально необходимые артефакты.

Подробности: `docs/chatgpt_web_workflow_ru.md`, `docs/local_agent_workflow_ru.md`, `docs/task_report_protocol_ru.md`.

## 8. Тестирование

- Для локальных тестов предпочитать stdlib `unittest`/существующий `tests_local`.
- Поведенческое изменение по возможности сначала фиксируется тестом.
- Локальные тесты не должны требовать реального сервера, если поведение можно проверить изолированно.
- Integration/E2E с реальным SSH/server/Yandex Cloud выполняются отдельным task и только с нужными gates.
- Канонический текущий сценарий стенда описан в `TEST_PLAN_YC_DILYAVM.md`; параметры облака перечитываются перед реальным прогоном и не считаются вечными.
