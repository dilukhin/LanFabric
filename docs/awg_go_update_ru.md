# AWG Go: совместимое обновление и возврат

Задача №28. Исходная основа — `master` после №31,
`392b1cabaf46eda3c66e3704530ab368fc6f5d8c`; версия остаётся 0.0.18.
Работа ограничена репозиторием и одноразовыми машинами GitHub Actions.

## Контракт

Обычный `patch` обновляет серверный модуль при совместимой смене последнего
числа версии. `patch --reinstall` позволяет установить проверенный модуль
той же версии. `patch --components` дополнительно устанавливает закреплённые
компоненты Go из поставки, указанной в новом модуле. Оба флага не вызывают `init`.
Компоненты скачиваются и проверяются до остановки VPN; произвольные URL,
непроверенные контрольные суммы и незаявленная смена формата состояния запрещены.

Новый модуль обязан поддерживать текущую схему обновления, сохранённую БД,
профиль, службу и ранее установленные компоненты. При будущей смене закреплённой
поставки её совместимый предшественник добавляется в проверенный перечень;
неизвестный или изменённый файл по-прежнему отклоняется. Понижение версии и
смена двух первых чисел запрещены. Миграция схемы БД этим путём не выполняется.

Эта основа должна присутствовать в первоначальной установке. Экспериментальная
редакция №31 намеренно отказывала в замене модуля поверх Go; её нельзя обновить
новым клиентом в обход этого отказа. Для такой установки потребуется отдельная
проверенная миграция. Рабочий v6 имеет другую службу и тоже сюда не относится.

## Порядок и отказ

1. Установщик проверяет права, журнал предыдущей операции и совместимость
   кандидата. Дочерняя проверка запускается без удержания блокировки состояния.
2. Приватный снимок root включает модуль, SQLite, ключи, параметры AWG,
   порт, выбор реализации, журнал установки, оба компонента и их описание.
   Контрольные суммы и права записываются в долговечный журнал `go-update.json`.
   Старый снимок удаляется только после проверки нового снимка и записи журнала.
3. Закрывается собственная защита. Останавливается доказанно свой процесс;
   незнакомый интерфейс или сокет запрещают очистку. Ожидание systemd выполняется
   вне общей блокировки состояния.
4. Файлы заменяются атомарно. Если VPN ранее работал, служба запускается и
   применяет полный профиль. До завершения проверяются фактическая готовность
   и побайтное сохранение данных, не входящих в обновление.
5. При отказе проверенный снимок возвращает прежние файлы и состояние службы.
   Если возврат не доказан, защита остаётся закрытой и требуется независимый
   доступ. Успешный возврат тоже возвращает ненулевой код исходного обновления.

При обрыве после записи журнала изменения участников и обычные изменения
runtime запрещены. Повтор проверенного обновления сначала возвращает прежний
снимок, затем повторяет операцию. Удаляется только учтённый приватный каталог
кандидата; незнакомый файл запрещает очистку. Сбой до записи первого журнала
не останавливает VPN, но может оставить неполный каталог: его содержимое
требует отдельной проверки, автоматическое удаление не обещается.

Завершённый снимок хранится приватно до следующего успешного приготовления
снимка или штатного `purge`. Секреты, содержимое SQLite и профили не включаются
в сообщения и отчёты. SSH-доверие, sudoers, чужие правила и системные пакеты
при обновлении не меняются. Это совместимый путь обновления кода, без смены
адресации и действующих клиентских профилей.

## Проверки

Локально пройдены 244 проверки, включая повреждённый журнал/снимок, запрет
изменений при незавершённой операции, отказ предварительной проверки и защищённую
передачу клиентом. Проверки CI привязываются к точному коммиту PR.

Настоящая служба испытывается на Ubuntu 22.04 и 24.04: обычный `init` получает
опубликованные файлы по HTTPS; затем проверяются успешное обновление, повтор без
перезапуска, повторная поставка компонентов, контролируемый отказ восстановления,
возврат профиля побайтно и повтор после принудительного завершения установщика.
SIGKILL процесса VPN, remove/reinstall/purge и защита чужих файлов остаются
в том же испытании. Результаты записываются после завершения CI.

Ubuntu 20.04 с исходным Python 3.8, перенос v6, холодная загрузка и реальные
клиенты остаются отдельными этапами. Проверка службы в CI не закрывает их.
